# 0007. Одна плоскость управления и ячейки как граница найма
- Статус: принято (15.11.2026), до аудита существующей системы

## Контекст

Факт: первый год систему ведёт один инженер. Позже куски отдают нанятым людям. Состояние лида, стоп-лист и аренда должны остаться у одного автора (0001, 0002). Почтовая и браузерная ячейки не делят хост.

## Варианты

### А. Микросервисы с первого дня

Суть: планировщик, аренда, стоп-лист, разбор ответов, исходящая таблица и каждый канал — отдельные сервисы.
За: независимая выкладка совпадает со списком найма. Падение разбора ответов не обязано ронять выдачу заданий. Каждая команда может иметь свой репозиторий и свой дежурный цикл.
Против: единственный писатель состояния лида размазывается по сети. Появляются распределённые транзакции там, где сейчас хватает одной транзакции Postgres. Один инженер эксплуатирует несколько контуров до того, как появился второй человек. Оценка: так вариант А из 0001 возвращается внутрь плоскости управления.

### Б. Один монолит на всё

Суть: почта, браузер, голос, устройства и база — один процесс и один образ.
За: один отладчик, одна миграция, один деплой. Для одного инженера это меньше всего движущихся частей. Контракт между модулями можно менять коммитом, не версией по сети.
Против: Playwright и SMTP в одном образе нарушают разнос хостов. Ячейку нельзя поставить у другого провайдера, не поставив туда всю базу. Нанятый на браузер получает доступ к лидам и паролям ящиков. Отказ браузера останавливает выдачу почты.

### В. Один процесс плоскости управления и отдельные ячейки

Суть: плоскость управления — один процесс (лиды, планировщик, аренда, стоп-лист, исходящая таблица). Ячейки — отдельные развёртывания у своих провайдеров за общим контрактом заданий и событий. Базы у ячейки нет.
За: радиус ущерба совпадает с 0001. Нанятому отдаётся ячейка или пакет с контрактом, а не вся база. Выкладка ячейки не требует миграции лидов. Приёмочный тест один на все каналы: повтор задания не уходит наружу второй раз.
Против: два способа развёртывания. Ломающее изменение схемы событий — общий день для всех ячеек. Если разбор ответов живёт внутри процесса плоскости, его нельзя отдать, не отдав ядро.

## Решение

Принят вариант В. Плоскость управления остаётся у ведущего инженера: схема, автомат лида, планировщик, аренда, стоп-лист, исходящая таблица webhook.

Отдавать можно только кусок с контрактом. В контракте каждого: схема задания и событий с версией, что считается успехом, какие отказы обязательны, чего делать нельзя, и общий приёмочный тест на повтор.

- Почтовая ячейка и доставляемость. Контракт: журнал на диске до закрытия аренды, нечитаемый счётчик закрывает отправку, секреты не уходят с узла, SPF, DKIM, DMARC и PTR этого адреса, приём входящих на этой же ячейке. Нельзя писать состояние лида.
- Браузерная ячейка. Контракт: тот же обмен, отдельный хост от почты, продление аренды на время сессии, зависание обязано отпустить аренду. Успех — принятая формой отправка, не живой процесс.
- Адаптер зарубежного голосового оркестратора. Контракт: «согласие» — факт, коммерческое предложение уходит только заданием в аренде. Своего распознавания и синтеза нет. Место записи фиксируется в журнале канала.
- Ячейка мессенджера. Контракт: тот же обмен, номер из пары идентичности, код SMS только из API компании для этого номера, почтовых секретов на хосте нет. Канал включается по отметке в записи. WhatsApp, ВКонтакте и Telegram — отдельные каналы одного контракта.
- Разбор ответов и эталон. Контракт: текст → JSON (интент, возражение, нужно ли КП), таймаут, доля ошибок, промпты сохраняются. Нет SMTP и нет записи в CRM.
- Развёртывание ячеек и мониторинг. Контракт: выкладка по одной ячейке, сердцебиение, оповещение «нет входящих N часов». Семантику аренды менять нельзя.
- Аналитика воронки. Контракт: только чтение. Нет записи в лиды и стоп-лист.

## Последствия

Проще нанимать на канал, не открывая базу. Сложнее держать версию контракта: ячейка обязана понимать текущую и предыдущую схему. Обязаны сделать: пакет разбора ответов без импорта модели лида и с отдельной выкладкой; фикстуры событий в репозитории; один тест на дубль, который гоняется и на обёртке старого Mailer, и на новой ячейке.

## Возражения, которые остались

К отказу от микросервисов и от единого монолита возражения нет. Разбор ответов можно отдать другому человеку только отдельным пакетом: без доступа к правилам движения лида и с отдельной выкладкой. Пока этого пакета нет, нанятый либо меняет ядро, либо не может обновить тексты запросов к модели отдельно. Мониторинг и аналитику как найм не открывать, пока оповещения — это Telegram и строка сердцебиения.

## Когда пересмотреть

Микросервис внутри плоскости управления заводить, только если отдельная выкладка разбора дважды за квартал заблокирована общим деплоем ядра. Новый процесс под канал не заводить: канал и так отдельная ячейка.
