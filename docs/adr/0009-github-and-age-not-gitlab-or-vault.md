# 0009. Код на GitHub, секреты через age
- Статус: принято 16.11.2026

## Контекст

Сервиса ещё нет. Код лежит на GitHub, на каждый push в GitHub Actions идут проверка стиля и pytest. Пароли новых ящиков должны остаться внутри компании: ящики не покупаются, учёт не отдаётся поставщику. Плоскость управления паролей не видит. Копия секретов ячейки лежит вне ячейки, иначе потеря диска оставляет живые ящики без входа.

Нужно начать инфраструктуру сейчас, иначе секреты и выпуск потом придётся перекладывать. При этом один инженер не должен сопровождать вторую платформу раньше первой ячейки.

## Варианты

### А. Свой GitLab и Vault с первого дня

Суть: код и раннеры в GitLab компании, пароли в Vault.
За: код не на чужом хостинге. Выдача секрета пишется в журнал. Второй человек может выдать пароль ячейке, не забирая мастер-ключ.
Против: GitLab и Vault надо обновлять, копировать и чинить до того, как есть что выкладывать. Запечатанный Vault останавливает отправку. Своего GitLab у нас нет, и ради одного репозитория его заводить рано.

### Б. GitHub для кода и тестов, age для паролей ячеек

Суть: репозиторий и конвейер остаются на GitHub. Пароль ящика — файл, зашифрованный age, на диске ячейки и такой же файл вне её. Ключ age не в репозитории и не в секретах GitHub: копия у инженера и копия у компании. В GitHub хранятся только служебные ключи конвейера. Свой runner GitHub Actions на машине компании ставится в день появления `stage`.
За: конвейер уже работает. Секрет не уезжает в настройки репозитория. Потеря ячейки не теряет пароль. Инструментов два: GitHub, который есть, и age, который не надо администрировать как сервис.
Против: пока ключ один на двоих, увольнение или потеря обеих копий закрывает все ячейки. Журнала «кто выдал пароль» нет. Код лежит на GitHub, не на сервере компании.

### В. Пароли в секретах GitHub

Суть: логин и пароль каждого ящика — secret репозитория, ячейка забирает их при выкладке.
За: ничего ставить не нужно.
Против: учёт ящиков оказывается у хостинга кода. Это противоречит правилу, что учёт остаётся внутри компании. Ротация и разделение по ячейкам в интерфейсе секретов репозитория неудобны уже на десятках ящиков.

## Решение

Принят вариант Б. Свой GitLab не поднимаем, пока у компании его нет и нет требования, что код обязан лежать только там. Vault не ставим, пока секреты выдаёт один человек.

Vault открываем снова, когда второй человек должен выдать пароль ячейке без копии мастер-ключа или когда одним файлом ключей уже неудобно пользоваться. До этого дня отправка от Vault не зависит.

Три контура, `dev`, `stage` и `prod`, с первого сервиса различаются значениями настроек. Образ на `prod` — тот, что прошёл `stage`. Образ помечается хешем коммита.

## Последствия

Проще начать: новый сервис секретов не блокирует первую ячейку. Обязаны сделать: файл ячейки шифруется age; копия файла лежит вне ячейки и вне базы лидов; ключ не коммитится; в GitHub нет паролей ящиков. Сложнее объяснить, что «инфраструктура начата» — это работающий конвейер и названное место секрета, а не установленный GitLab.

## Когда пересмотреть

Свой GitLab — если он уже есть у компании и код обязан переехать. Vault — когда появляется второй человек, выдающий секреты, или когда ключей больше, чем умещается в одном файле age. Runner на машине компании — в день, когда появляется `stage` внутри её сети.
