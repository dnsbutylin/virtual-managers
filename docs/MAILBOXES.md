# Почтовые ящики: как заводим и как ведём

Редакция от 17.11.2026. Написана до аудита существующих ящиков.

Факты о провайдерах и регистраторах взяты из официальных справок на 15.11.2026. Трудозатраты и выводы — оценки, замеров нет. Рабочая схема — в [adr/0008](adr/0008-gmail-fleet-domain-conveyor-is-a-test.md): новые ящики Gmail компания создаёт сама, уже работающие 40–60 пар в систему не передаются. Разделы про домены описывают тест, а не закупку первого месяца.

## 1. Коротко

- Сделать ящики несвязанными нельзя, пока все они продают одну услугу одной компании: текст, ссылки и название в письме связывают их при любой схеме.
- Связи между ящиками не вызывают блокировку, а определяют, как далеко она разойдётся. Вызывают её жалобы, шаблонный текст и отказы доставки.
- Рабочий узел новой системы — новая пара «ящик Gmail + номер компании». Такие пары создаёт компания: 117, 152 и 198 на месяцы 1–3 при 100 письмах в день. Уже работающие 40–60 пар остаются в старой отправке. К номеру есть доступ через веб или API, код SMS для входа приходит по API компании.
- Общего ящика для ответов нет: отвечает та ячейка, которая отправляла.
- Домены, если тест будет запущен, остаются маленьким узлом: 4 ящика на домен, один домен на организацию у провайдера, три провайдера. Заводятся они скриптами через официальные API. Руками остаются создание организаций и пароли приложений. До решения по тесту этот раздел не исполняется.

## 2. Что связывает ящики между собой

| Связь | Кто её видит | Свои домены | Бесплатные ящики |
|---|---|---|---|
| Текст письма, ссылки, название компании, телефон в подписи | провайдер отправителя и провайдер получателя | есть | есть |
| Жалобы и отказы одних и тех же получателей | провайдер получателя | есть | есть |
| Домен отправителя | все | узел на 4 ящика | своего узла нет |
| Организация у почтового провайдера, плательщик | провайдер отправителя | есть | нет |
| Владелец домена в whois | все | есть: правила зоны .ru требуют показывать название и ИНН юрлица (живой запрос не проверял) | нет |
| Номер телефона при регистрации | провайдер отправителя | нет | по номеру на ящик |
| Адрес, с которого программа ходит по SMTP и IMAP | провайдер отправителя | около 40 ящиков на адрес ячейки | то же |
| Общий ящик для сбора ответов | провайдер отправителя | убираем | сейчас есть |

Строки «текст письма» и «жалобы» не зависят от схемы ящиков. Убрать их можно, только скрыв, кто пишет и что предлагает. Проект этого не делает: иначе письмо перестаёт быть предложением компании.

## 3. Чем схема отличается от варианта «10 ящиков на домен»

На встрече звучал вариант: домен, один провайдер, 10 ящиков. У него один недостаток, который и нужно убрать: блокировка домена или кабинета снимает всё сразу. Домен и адрес при этом остаются узлами и в предлагаемой схеме.

Отличия:

- 4 ящика на домен. Потеря домена — около 1% мощности.
- Три провайдера, доля каждого не выше 40%.
- Один домен на одну организацию там, где иначе домены склеиваются (Яндекс 360, см. раздел 4).
- Ячейка обслуживает около 40 ящиков со своего адреса. Один адрес не видит все 350.
- Ответы собирает та же ячейка, общего ящика нет.

Основой объёма после 16.11.2026 являются уже имеющиеся ящики Gmail, а не эта схема. Схема доменов нужна как устройство теста. Риски Gmail при этом не отменяются: личный ящик Gmail не описан провайдером как ящик для рассылки, и правило провайдера может остановить сразу весь класс. Это принятое свойство текущей схемы. Снимает вопрос не заказ доменов авансом, а замер: доля во «Входящие», доля ответов и число остановок. Экономика конвейера — в [VISION.md](VISION.md), раздел 2.

## 4. Как устроены провайдеры

| Вопрос | Яндекс 360 | VK WorkSpace | Хостинговая почта (Timeweb, Beget) |
|---|---|---|---|
| Несколько доменов в одном кабинете | дополнительные домены — алиасы основного: каждый ящик получает адрес на каждом домене | домены независимы, до 30 на учётную запись | не проверено |
| Что это значит для нас | один домен — одна организация; на 140 ящиков около 35 организаций | две учётные записи на 35 доменов | — |
| Создание организации или кабинета | метода в API не найдено, вручную | вручную | вручную, один раз |
| Добавление домена, DKIM, создание ящиков | есть в API | есть в документации `biz.mail.ru`; действует ли она сейчас — не подтверждено | у Beget есть метод создания ящика; у Timeweb не найден |
| Пароль приложения для SMTP и IMAP | нужен; метода в API не найдено | нужен | не проверено |
| Опубликованный лимит отправки | 300 получателей в сутки через SMTP, снижается при подозрении на рассылку | число не опубликовано; есть часовой лимит | Timeweb: 2000 писем в сутки на все ящики аккаунта |
| Цена ящика | 319 ₽/мес («Минимальный»); тариф за 279 ₽ — от 10 сотрудников на организацию | 309 ₽/мес | Timeweb: 95–120 ₽/мес |

Что это меняет в прежних документах:

- В смете ящик Яндекса посчитан по 319 ₽. Тариф 279 ₽ при 4 ящиках на организацию недоступен. Разница на 140 ящиках — 5 600 ₽ в месяц, она уже входит в итог 231–321 тыс.
- У Timeweb при 40 письмах в день на один аккаунт помещается не больше 50 ящиков.
- Третий провайдер не выбран. Кандидаты — в таблице; лимиты и цены Beget не найдены.

## 5. Что автоматизируется

| Шаг | Как | Руками |
|---|---|---|
| Регистрация доменов | API регистратора (REG.RU, Timeweb); данные юрлица вводятся один раз | договор с регистратором, оплата |
| DNS: MX, SPF, DKIM, DMARC | API DNS; один скрипт на все домены | нет |
| Организация или кабинет у почтового провайдера | — | да: около 35 у Яндекса, 2 у VK |
| Домен в организации, проверка, DKIM | API провайдера | у VK — если API не действует |
| Создание ящиков | API провайдера | то же |
| Пароль приложения | — | да, вход в каждый ящик |
| Запись ящика в систему, шифрование пароля, привязка к ячейке | наш скрипт | нет |
| Проверка: письмо на контрольный ящик, подписи SPF и DKIM сходятся | наш скрипт | нет |
| Прогрев | планировщик по графику | нет |

Итог каждого запуска — файл учёта: домен, провайдер, организация, ящики, ячейка, дата начала прогрева. Повторный запуск ничего не дублирует.

Оценка ручного труда при 3–5 минутах на пароль приложения и 5–10 минутах на организацию: первая партия в 90 ящиков — 5–9 часов, все 351 — 20–35 часов. Это работа по чек-листу, её можно отдать помощнику с первой же партии. Оценка без замера; первая партия покажет.

## 6. Что остаётся связанным и почему это приемлемо

Все домены оформлены на одно юрлицо и оплачены с одного счёта. Провайдер, который захочет их связать, свяжет. Я не предлагаю это скрывать: оформление доменов на частных лиц переносит право на домен с компании на сотрудника, и это решение руководителя и юриста, а не инженера.

Защита строится на другом:

- низкий объём на ящик и текст, который не выглядит шаблоном;
- отписка в каждом письме и немедленный стоп-лист;
- автопауза ящика и домена по отказам доставки и жалобам;
- резерв прогретых доменов, который тоже понемногу отправляет.

## 7. Уже работающие ящики и новые

40–60 ящиков Gmail, которые уже пишут, в новую систему не переносим. Они продолжают работать как сейчас, объём на них не поднимаем.

Новые ящики компания создаёт сама и передаёт в учёт:

- Пара с номером компании. В паре хранится способ взять код SMS из API этого номера.
- Раскладываем по ячейкам так, чтобы один адрес ячейки не видел весь парк. Пара с ячейки не переезжает. Метка гео лежит на ячейке.
- История действий с ящика и профиль хранятся в карточке нашей базы: операционная система, GeoIP, пол и остальные поля этого профиля. Пароль остаётся на ячейке. GeoIP дублируется меткой на ячейке.
- С первого дня считаем по каждому: письма в день, отказы доставки, открытия, ответы, блокировки.

Первые три пары заводит инженер, вручную, с номера вендора и кода из SMS API. Дальше регистрацию ведёт отдельный человек. Лимит ящика — 100 писем в день. Регистрация 6 часов в день: 5 минут на пару дают около 72 пар в день и 117 пар за 2 рабочих дня, 15 минут — около 24 пар в день и 117 пар за 5 рабочих дней. Покупка аккаунтов у поставщиков не используется. Контракт задания один. Планировщик различает ящик Gmail и ящик доменного теста пометкой типа и лимитом.

Сравнение Gmail и своих доменов, если тест запущен:

- две группы: новые ящики Gmail и домены после прогрева;
- один сегмент получателей, один текст, один объём на ящик;
- две-три недели;
- метрики: доля во «Входящих», доля ответов, отказы доставки, сколько доменов встали на паузу.

Как устроены такие опыты — в [TESTING.md](TESTING.md). Решение, при котором домены входят в рабочую схему, — в [adr/0008](adr/0008-gmail-fleet-domain-conveyor-is-a-test.md).

## 8. Номера и вход в ящик

Номер принадлежит компании. Доступ к нему есть через веб или API. Код из SMS для входа в учётную запись компании читается через API компании и относится к номеру этой пары.

В проект не входит:

- скрипт, который сам регистрирует ящики;
- обход капчи;
- подмена отпечатка браузера и набор прокси, чтобы регистрации выглядели пришедшими из разных мест;
- переписка ящиков между собой, чтобы снизить долю жалоб.

Мощность почты равна числу пар, которые компания создала, умноженному на измеренный дневной лимит. На 350 тыс. писем в месяц при 100 письмах в день нужно 117 новых ящиков. Нехватка закрывается следующими парами, которые создаёт компания, а не регистрацией из кода и не переносом уже работающих ящиков.

## 9. Общий ящик Collector

Отказ от общего ящика всю проблему связей не решает. Он убирает две вещи:

- единую точку отказа: блокировка одного ящика останавливает приём всех ответов;
- самую явную связь: правило пересылки или сбор почты, которые указывают с каждого ящика на один адрес.

Связи через текст, ссылки и получателей остаются. Как именно устроен сбор сейчас — пересылка, «сборщик почты» провайдера или чтение каждого ящика почтовой программой с одного адреса — станет ясно на аудите. В третьем случае общего ящика как узла нет. Связь идёт через адрес сборщика: ячейки сокращают число ящиков на одном адресе с 350 до 40.

## 10. Открытые вопросы

До замера, без назначения исполнителя:

- кто создаёт пары после первой ячейки. Первые пары инженер заводит сам, с номера и кода SMS, и засекает время одной пары. Решение — по числу нужных ящиков и по этому времени. Дневной лимит снимает замер;
- как сейчас собираются ответы на уже работающих ящиках, не забирая сами ящики;
- как устроены API номера и SMS.

К доменному тесту, и только если он запущен:

Проверить на первой партии теста:

- действует ли API VK WorkSpace из документации `biz.mail.ru`;
- минимальное число сотрудников на тарифе Яндекса «Минимальный»;
- фактический лимит отправки VK WorkSpace;
- третий провайдер: лимиты и цена;
- реальное время на один ящик.
